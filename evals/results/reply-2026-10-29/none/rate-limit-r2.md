## Token bucket, 쉽게 설명

**비유:** 사용자마다 "토큰 통"이 하나씩 있습니다.
- 통에는 최대 100개까지 토큰이 담깁니다.
- 요청 1번 = 토큰 1개 소비. 통이 비어 있으면 요청은 거절(HTTP 429)됩니다.
- 토큰은 일정 속도로 자동 충전됩니다. 분당 100회라면 약 0.6초마다 1개(초당 ≈1.67개).
- 통이 가득 차 있으면 더 쌓이지 않습니다.

그래서 한동안 조용하던 사용자는 최대 100개를 한꺼번에(burst) 쓸 수 있고, 그 후에는 충전 속도(평균 분당 100회)에 맞춰서만 요청할 수 있습니다.

## 이 경우에 맞나?

**대체로 맞습니다.** 이유:
- 사용자별 제한 + 평균 속도 제한이라는 목적에 잘 맞습니다.
- 정상적인 짧은 몰림(페이지 로드 시 API 여러 개 호출 등)을 허용해서 사용자 경험이 좋습니다.
- 구현이 가볍습니다. 사용자당 "남은 토큰 수 + 마지막 갱신 시각" 두 값만 저장하면 되고, 타이머 없이 요청이 올 때 경과 시간으로 계산하면 됩니다. Redis와 Lua 스크립트로 원자적으로 처리하는 방식이 흔합니다.
- 업계 표준에 가까운 방식입니다(Stripe, AWS 등).

**주의할 점:**
- **"정확히 어느 1분 구간에도 100회 이하"는 보장하지 않습니다.** 통이 가득 찬 상태에서 100회를 쓰고 곧바로 충전분이 더해지면, 짧은 시간에 100회를 초과해 보이는 구간이 생길 수 있습니다. 엄격한 보장이 필요하면 sliding window (log 또는 counter)가 더 적합합니다.
- **burst를 줄이고 싶다면** 버킷 크기를 100보다 작게(예: 20) 잡고 충전 속도만 분당 100으로 유지하면 됩니다.
- 여러 서버에서 돌린다면 상태를 Redis 같은 공유 저장소에 두고 원자적으로 갱신해야 합니다.
- 클라이언트가 재시도할 수 있도록 `429`와 함께 `Retry-After`, `X-RateLimit-Remaining` 헤더를 내려 주는 것이 좋습니다.

## 요약

| 요구사항 | 추천 |
|---|---|
| 평균 분당 100회, 약간의 burst 허용 | **Token bucket** |
| 어떤 1분 구간에서도 절대 100회 초과 불가 | Sliding window |
| 단순함 최우선, 경계 오차 허용 | Fixed window counter |

특별히 엄격한 요구(과금, 외부 API 쿼터 등)가 없다면 동료의 제안대로 token bucket으로 가셔도 좋습니다.
