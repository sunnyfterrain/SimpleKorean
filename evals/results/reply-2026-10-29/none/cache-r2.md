코드를 보지 않고 일반적인 원인을 말씀드립니다. 작업 디렉터리(/private/tmp)에는 해당 프로젝트가 없는 것 같습니다.

## 왜 그런가

"최대 10분"이라면 거의 확실히 **캐시 TTL이 600초**이기 때문입니다. 흔한 구조는 이렇습니다.

1. 읽기: Redis 조회 → 없으면 DB 조회 → `SET key value EX 600`
2. 쓰기: DB만 갱신하고 **캐시는 그대로 둠**
3. 결과: 키가 만료될 때까지 최대 10분간 옛 가격이 나갑니다.

이른바 cache-aside에서 쓰기 시 무효화가 빠진 경우입니다. 가격 변경 경로가 여러 곳이면(관리자 화면, 배치, 외부 연동 등) 일부만 무효화하는 경우도 많습니다.

## 어떻게 고치나

**1. 쓰기 시 무효화 (기본 해법)**
DB 커밋 **후에** 캐시 키를 삭제합니다.
```
UPDATE price ... ; COMMIT;
DEL price:{productId}
```
- 갱신(SET)보다 삭제(DEL)가 경쟁 상태에 안전합니다.
- 커밋 전에 지우면, 그 사이 다른 요청이 옛 값을 다시 캐시에 채울 수 있습니다.
- DEL이 실패할 수 있으니 재시도하거나, 아웃박스/이벤트(CDC 등)로 비동기 무효화하면 더 견고합니다.

**2. 모든 쓰기 경로를 한곳으로 모으기**
가격을 바꾸는 코드가 repository/service 한 곳만 거치게 하고, 무효화를 거기에 둡니다. 배치나 직접 SQL로 바꾸는 경로가 가장 흔한 누락 지점입니다.

**3. TTL은 안전망으로만**
TTL을 줄이거나(예: 30~60초) 지터를 넣어 두면, 무효화가 한 번 실패해도 오래 가지 않습니다. 가격처럼 민감한 값은 TTL에만 의존하면 안 됩니다.

**4. 필요하면 추가 보강**
- 키에 버전을 넣기: `price:{id}:v{version}`
- 결제나 주문 시점에는 캐시를 쓰지 않고 DB 가격을 재확인하기. 화면 표시는 약간 늦어도, 청구 금액은 항상 정확해야 합니다.

## 확인 방법
- 가격 변경 코드에서 `DEL`/`unlink`/`evict` 호출이 있는지 찾습니다.
- 캐시 키 이름이 읽기와 삭제에서 정확히 같은지 봅니다. 접두사나 직렬화가 다르면 무효화가 조용히 실패합니다.
- Redis에서 `TTL price:{id}`로 만료 시간이 실제로 600초 근처인지 확인합니다.

코드 위치를 알려주시면 실제 읽기/쓰기 경로를 보고 구체적으로 짚어 드리겠습니다.
