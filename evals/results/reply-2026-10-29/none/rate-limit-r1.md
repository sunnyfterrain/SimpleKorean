## Token bucket 쉬운 설명

**양동이 비유**를 생각하면 됩니다.

- 사용자마다 양동이가 하나 있고, 안에 "토큰"이 들어 있습니다. 최대 100개까지 담깁니다.
- API 요청 1회마다 토큰 1개를 꺼내 씁니다. 토큰이 없으면 요청은 거절됩니다(HTTP 429).
- 토큰은 일정 속도로 다시 채워집니다. 분당 100회라면 약 0.6초마다 1개(초당 약 1.67개)씩 채워지고, 100개가 넘으면 버려집니다.

그래서 한동안 요청이 없던 사용자는 양동이가 가득 차 있어서 100개를 한꺼번에 보낼 수 있습니다(버스트 허용). 그 뒤로는 채워지는 속도만큼만 꾸준히 보낼 수 있습니다.

## 이 경우에 맞나?

**대체로 맞습니다. 대부분의 API 레이트 리밋에 좋은 기본 선택입니다.**

장점
- 구현이 단순합니다. 사용자당 "남은 토큰 수"와 "마지막 갱신 시각" 두 값만 저장하면 됩니다. Redis에 넣기도 쉽습니다.
- 메모리 사용이 적고 계산이 O(1)입니다.
- 짧은 순간의 몰림을 허용해서 실제 사용자에게 덜 불편합니다.

주의할 점
- **엄격한 "어느 60초 구간에서도 100회 이하"가 아닙니다.** 버스트 때문에 구간 경계에서 짧게 100회 이상 나갈 수 있습니다. 예를 들어 가득 찬 상태에서 100회를 쓰고, 1분 뒤 다시 거의 100회를 쓸 수 있습니다. 평균은 분당 100회지만 순간 최대는 더 클 수 있습니다.
- 버스트가 백엔드에 부담이 된다면 버킷 크기를 100보다 작게(예: 20~30) 하고 채우는 속도만 분당 100회로 두면 됩니다.
- 여러 서버에서 쓴다면 상태를 Redis 등에 공유해야 하고, 읽기-계산-쓰기를 Lua 스크립트 같은 원자적 연산으로 처리해야 합니다.

## 대안과 비교

| 방식 | 특징 | 언제 적합 |
|---|---|---|
| Fixed window | 가장 단순하지만 경계에서 2배까지 몰릴 수 있음 | 대략적 제한이면 충분할 때 |
| Sliding window log | 가장 정확하지만 요청마다 기록을 저장해 메모리 큼 | 엄격한 정확도가 필수일 때 |
| Sliding window counter | 정확도와 비용의 절충 | 엄격함과 효율을 모두 원할 때 |
| Token bucket | 단순하고 버스트 허용 | 일반적인 API 제한 |

## 결론

"분당 100회" 정도의 일반 사용자 제한이라면 token bucket을 쓰셔도 좋습니다. 다만 "정확히 어느 1분 구간에서도 100회 초과 금지"가 요구사항이라면 sliding window 방식이 더 맞습니다. 그 요구사항이 엄격한지 동료분과 먼저 확인해 보세요.
