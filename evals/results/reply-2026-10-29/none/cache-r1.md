코드를 보지 않고 일반적인 원인부터 말씀드리면, 최대 10분이라는 숫자는 거의 확실히 **캐시 TTL이 600초**로 설정돼 있고, 가격 변경 시 캐시를 무효화하지 않기 때문입니다. (실제 코드는 아직 확인하지 않았습니다. 프로젝트 경로를 알려주시면 정확히 짚어드리겠습니다.)

## 왜 그런가

전형적인 cache-aside 패턴입니다.

1. 읽기: Redis 조회 → 없으면 DB 조회 후 `SET key value EX 600`
2. 쓰기: DB만 업데이트하고 Redis 키는 그대로 둠
3. 결과: 키가 만료될 때까지(최대 10분) 옛 가격이 반환됨

"최대"인 이유는 마지막으로 캐시가 채워진 시점부터 TTL이 흐르기 때문입니다. 변경 직전에 캐시됐다면 거의 10분, 오래전에 캐시됐다면 곧 갱신됩니다.

## 어떻게 고치나

**1. 쓰기 시 캐시 무효화 (가장 기본적인 해결책)**
```python
db.update_price(product_id, new_price)
redis.delete(f"product:{product_id}")   # 다음 읽기가 DB에서 새로 채움
```
- 가격 수정 경로가 여러 곳(관리자, 배치, 외부 연동)이면 **모두** 같은 함수를 거치게 하세요. 한 곳만 빠져도 같은 문제가 재발합니다.
- 상품 목록, 검색 결과, 장바구니처럼 가격이 **파생 캐시**에 들어가 있다면 그 키들도 같이 지워야 합니다.

**2. 순서와 경합 주의**
- 순서는 "DB 커밋 → 캐시 삭제"로 하세요. 트랜잭션 커밋 전에 지우면 다른 요청이 옛 값을 다시 캐시에 채웁니다.
- 읽기 요청이 삭제 직전에 옛 값을 읽어두었다가 삭제 후 SET 하는 경합도 있습니다. 완벽히 막으려면 버전 번호를 키에 넣거나(`product:{id}:v{version}`), 지연 이중 삭제(수백 ms 후 한 번 더 삭제)를 쓰세요.

**3. TTL은 안전망으로 유지하되 줄이기**
무효화가 누락돼도 피해가 제한되도록 가격처럼 민감한 데이터는 TTL을 30~60초로 줄이는 것도 방법입니다.

**4. 다른 선택지**
- 가격 변경 이벤트를 발행하고 구독자가 캐시를 갱신 (서비스가 여러 개일 때)
- write-through: 쓰기 시 DB와 Redis를 함께 갱신
- 가격만 캐시하지 않고 항상 DB에서 읽기 (트래픽이 감당 가능하다면 가장 단순)

## 먼저 확인할 것
- `EX 600`/`expire`/`setex` 등으로 TTL이 600인 곳
- 가격을 쓰는 모든 코드 경로에 `delete`가 있는지
- CDN이나 브라우저 캐시(`Cache-Control: max-age=600`)가 따로 끼어 있지 않은지. Redis를 고쳤는데도 10분이 남는다면 이쪽이 원인입니다.

코드 위치를 알려주시면 실제 원인과 수정 지점을 직접 찾아드리겠습니다.
