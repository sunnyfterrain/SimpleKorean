**상황에 따라 다르지만, 기본 원칙은 이렇습니다.**

## 핵심 규칙
- **공유된(push된) 브랜치의 히스토리는 rebase 하지 않는다.** 다른 사람이 그 커밋을 기반으로 작업 중일 수 있어서, 히스토리를 바꾸면 충돌과 혼란이 생깁니다.
- **내 로컬(혹은 나만 쓰는) 브랜치는 rebase 해도 안전하다.**

## Merge
- 두 브랜치의 히스토리를 그대로 보존하고, 합치는 지점에 머지 커밋을 만듭니다.
- **장점:** 안전함, 실제 작업 흐름이 그대로 기록됨, 충돌을 한 번만 해결하면 됨
- **단점:** 머지 커밋 때문에 히스토리가 지저분해질 수 있음
- **적합한 경우:** `feature → main` 통합, 여러 명이 함께 쓰는 브랜치, 히스토리를 건드리고 싶지 않을 때

## Rebase
- 내 커밋들을 대상 브랜치의 최신 끝 위에 다시 쌓아서 일직선 히스토리를 만듭니다.
- **장점:** 깔끔한 선형 히스토리, `git log`/`bisect` 보기 편함
- **단점:** 커밋 해시가 바뀜(히스토리 재작성), 커밋마다 충돌을 해결해야 할 수 있음, 잘못 쓰면 위험
- **적합한 경우:** 내 feature 브랜치를 최신 `main`에 맞춰 업데이트할 때, PR 올리기 전 커밋 정리(`rebase -i`)

## 실무에서 흔한 조합
1. feature 브랜치에서 작업하다 `main`의 변경을 가져오고 싶을 때 → `git rebase main` (혼자 쓰는 브랜치라면)
2. PR을 `main`에 합칠 때 → 팀 정책에 따라
   - **Merge commit:** 히스토리 보존
   - **Squash merge:** PR 하나를 커밋 하나로 압축 (가장 흔함)
   - **Rebase merge:** 선형 히스토리 유지

## 한 줄 요약
- 혼자 쓰는 브랜치 정리/업데이트 → **rebase**
- 공유 브랜치 통합 → **merge**
- 잘 모르겠거나 팀 규칙이 없다면 → **merge(또는 squash merge)가 더 안전한 선택**

팀에서 이미 정해둔 컨벤션이 있다면 그것을 우선 따르세요.
