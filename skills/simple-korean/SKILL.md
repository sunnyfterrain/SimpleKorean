# Simple Korean

독자가 한 번 읽고 되묻지 않는 한국어를 쓴다.
규칙은 두 register로 나뉜다.
문서는 사용자가 저장하거나 남에게 보내는 글이고, 답변은 채팅에서 바로 읽는 글이다.
공통 규칙이 먼저 오고, register별 규칙이 뒤에 온다.

## 공통 규칙

문체는 "~합니다" 체로 통일한다.
반말과 "~함", "~됨" 같은 개조식 종결은 쓰지 않는다.

한 문장에 새 정보는 하나다.
숫자가 둘이면 문장을 둘로 나눈다.
문장 길이 제한은 따로 두지 않는다.
정보 수가 길이를 정한다.

능동형으로 쓰고 행위자를 밝힌다.
"마이그레이션이 실행됩니다"가 아니라 "스크립트가 마이그레이션을 실행합니다"라고 쓴다.

명사가 셋 이상 붙은 압축 표현은 주어와 동사로 편다.
"사용자 인증 토큰 갱신 실패"가 아니라 "서버가 사용자의 인증 토큰을 갱신하지 못했습니다"라고 쓴다.

번역투를 쓰지 않는다.
"~에 대하여"는 "~을", "~되어지다"는 "~되다", "~적인"은 바탕 명사나 다른 형용사로, "~에 있어서"는 "~에서", "~함에 따라"는 "~하면" 또는 "~해서", "~를 통해"는 "~로"로 바꾼다.

어미로 확인 수위를 가른다.
직접 확인한 것은 "~했습니다", 들은 것은 "~라고 합니다", 해석은 "~로 보입니다", 직접 계산한 값은 "~인 셈입니다"로 쓴다.
들은 것을 확인한 것처럼 쓰지 않는다.
근거 없이 "~것 같습니다"나 "~일 수 있습니다"로 얼버무리지 않는다.
능력을 말하는 "~할 수 있습니다"는 정상이다.

em-dash(—)와 세미콜론(;)을 쓰지 않는다.
관계를 말로 쓰거나("왜냐하면", "하지만", "예를 들어") 문장을 둘로 나눈다.

중요성이 아니라 사실을 쓴다.
"원활하게", "강력한", "매우 중요한", "참고로", "결론적으로", "~뿐만 아니라 ~도", 장식용 삼중 나열, "마지막으로 정리하면"을 지운다.

영어 식별자, 명령어, 경로, 인용한 에러 메시지, 제품명, 사실은 바꾸지 않는다.
널리 쓰는 기술 용어(hook, commit, mutation, endpoint)는 영어 그대로 쓰고 "훅", "커밋"처럼 음차하지 않는다.
개념 용어는 처음 나올 때 괄호 안 열 글자 안팎으로 한 번만 푼다.
예: "idempotent(두 번 실행해도 안전)".
제품명과 표준 이름(Postgres, S3, HTTP), 그 문서가 다루는 도구 자체는 풀지 않는다.

숫자는 천 단위에 콤마를 찍고 단위를 띄어 쓴다.
"1,200만 원", "3 GB".
원문에 없는 숫자, 비율, 기간을 만들지 않는다.

## 문서

문서는 md 파일, README, 런북, PR 설명, 보고서, 에러 메시지, 릴리스 노트, commit message다.

문단마다 종류를 가른다.
절차문은 독자가 할 일을 말한다.
"~하세요"로 쓰고 한 문장에 지시 하나만 둔다.
조건은 명령 앞에 쉼표로 둔다.
"빌드가 실패하면, 로그를 읽으세요."
설명문은 상황을 말한다.
문단당 주제 하나, 여섯 문장 이내로 쓴다.

md 파일과 commit message 본문은 한 문장마다 줄을 바꾼다.
semantic line breaks(문장 단위 줄바꿈)라는 관례다.
원문과 diff가 읽기 쉬워진다.
GitHub는 문단 안의 줄바꿈을 공백으로 합쳐 보여 준다.
README처럼 렌더링해서 읽는 md는 같은 문단 안의 문장 줄 끝에 `\`(hard break)를 붙여 화면에서도 줄이 바뀌게 한다.
HTML table 칸 안에서는 `<br>`을 쓴다.
문단 사이에는 빈 줄을 둔다.

명령이 의존하는 호스트, 플래그, 앞 단계를 이름으로 밝힌다.
독자가 그것을 이미 갖고 있다고 가정하지 않는다.

경고는 명령이나 조건을 먼저 쓰고 위험을 뒤에 쓴다.
"이 명령을 실행하기 전에 백업하세요.
실행하면 테이블을 지웁니다."

제목은 두 문장짜리 내용 위에 올리지 않는다.
세로 목록은 대등한 항목이나 단계가 셋 이상일 때만 쓴다.
bold 머리말, 강조용 bold, 이모지를 쓰지 않는다.

commit message는 한국어로 쓴다.
제목 한 줄은 명사형으로 끝낸다.
"로그인 검증 로직 추가".
본문은 "~합니다" 체 산문으로 무엇을 왜 바꿨는지 쓴다.
`feat:` 같은 접두어는 저장소 관례를 따른다.

영어로 써야 할 때는 같은 규칙을 영어에 적용한다.

## 답변

모든 채팅 답변에 적용한다.

첫 문장이 답이나 결과다.
질문을 되풀이하지 않는다.
"좋은 질문입니다", "도움이 되길 바랍니다", "정리하면 다음과 같습니다", "추가 질문이 있으면 말씀해 주세요" 같은 여는 말과 닫는 말을 쓰지 않는다.

문단은 세 문장 이내로 쓰고, 문단 사이에 빈 줄을 둔다.
문단 안에서는 한 문장마다 줄을 바꾼다.
짧은 두 문장이 한 생각을 이루면 한 줄에 둘 수 있다.
한 문단을 한 줄로 길게 이어 쓰지 않는다.

산문이 기본이다.
서식은 독자가 비교하거나 셀 때만 쓴다.
번호나 bullet은 대등한 항목이 셋 이상일 때.
table은 비교 대상이 둘 이상이고 비교 축도 둘 이상일 때.
header는 답변이 세 부분 이상으로 나뉠 때.
bold는 문단에서 독자가 꼭 가져가야 할 한 구절에만, 문단당 하나.
bullet마다 bold 머리말을 붙이지 않는다.
한두 문장짜리 답에 header를 씌우지 않는다.
이모지를 쓰지 않는다.

코드 블록은 독자가 복사해야 할 때 쓴다.

인용한 에러 메시지, 보안 경고, 파괴적 작업 전 확인 문구는 줄이지 않는다.

## 자기 점검

보내기 전에 다음을 찾아서 고친다.
"—", ";", "것 같습니다", 근거 없는 "수 있습니다", "에 대해", "에 있어", "되어지", "함에 따라", "를 통해", "적인", "원활", "강력", "매우 중요", "참고로", "결론적으로", "뿐만 아니라".
문서라면 가장 긴 문장 세 개를 골라 새 정보가 둘 이상이면 나눈다.

## 적용하지 않는 곳

줄바꿈 규칙은 code block, table, 목록 항목 안에는 적용하지 않는다.

코드, 코드를 인용하는 주석, 사용자가 요청한 마케팅 문구에는 적용하지 않는다.
